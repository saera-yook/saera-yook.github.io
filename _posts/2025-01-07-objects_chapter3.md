객체지향 패러다임의 본질

객체들의 책임과 협력이 어느 정도 자리를 잡은 후에 구현 매커니즘을 사용. 너무 이른 시기에 구현 초점 → 변경 어렵고 유연하지 못한 코드를 낳는다.

## 협력

- 객체의 존재 이유는 협력에 참여하고 있다는 것 단 하나이다.
- 객체가 수행하는 행동의 동기를 제공
- 객체를 설계하는 데 필요한 문맥을 제공
- 상태는 객체의 행동에 필요한 정보에 의해 결정, 행동은 협력 안에서 객체가 처리할 메시지로 결정

## 책임

객체지향 설계에서 가장 중요

책임이 객체지향 애플리케이션 전체의 품질을 결정

### 하는 것

- 객체 생성, 계산 수행 등 스스로 하는 것
- 다른 객체의 행동을 시작시키는 것
- 다른 객체의 활동을 제어하고 조절하는 것

### 아는 것

- 사적인 정보에 관해 아는 것
- 관련된 객체에 관해 아는 것
- 자신이 유도하거나 계산할 수 있는 것에 관해 아는 것

- 책임이 외부의 인터페이스와 내부의 속성을 결정
- 책임과 메시지의 크기는 다르다. 책임이 더 추상적이고 개념적으로도 크다.
- 하는 것과 아는 것은 밀접하게 연관돼 있다.
- 자신이 할 수 없는 작업을 도와줄 객체를 알고 있을 책임이 있다.

### CRC 카드

후보, 책임, 협력자를 기록한 카드

앞면: 후보의 목적을 기술, 외부에 제공해야하는 서비스

뒤면: 목적을 세분화해서 무엇을 알고 무엇을 해야하는지에 대한 책임을 적는다. 우측에 함께 협력할 협력자들을 나열한다.

- 효과적으로 일하는 사람들은 추상적이고 가상적인 것보다는 구체적이고 실재적인 것을 사용하는 경향이 있다.

### 책임 할당

- 책임 수행에 필요한 정보를 가장 잘 알고 있는 전문가에게 그 책임을 할당하는 것. 책임 할당을 위한 정보 전문가 패턴.
- 객체지향 설계는 협력에 필요한 메시지를 찾고 메시지에 적절한 객체를 선택하는 반복적인 과정
- 최종 결과물은 객체들의 인터페이스와 오퍼레이션의 목록 ⇒ 코드로 구현하면 구현이 됨.

### 책임 주도 설계(RDD)

### 메시지가 객체를 결정한다.

- 객체가 최소한의 인터페이스를 가질 수 있게 된다.
- 충분히 추상적인 인터페이스를 가질 수 있게 된다. 무엇을 하는지는 메시지로 표현하지만 어떻게 수행하는지를 노출하면 안된다.

### 행동이 상태를 결정한다.

- 객체에 필요한 상태를 결정하고, 상태에 필요한 행동을 결정하면 내부 구현이 인터페이스에 노출되도록 만들어 캡슐화를 저해한다.
    - 내부 구현에 초점을 맞춘 설계 방법: 데이터 주도 설계(DDD)

## 역할

역할에게 책임을 할당한다.

- 익명의 역할을 찾고 그 역할을 수행할 수 있는 객체를 선택
- 협력 안에서 대표자를 찾고, 두 종류의 객체를 교대로 바꿔 끼울 수 있는 일종의 슬롯으로 생각. 슬롯이 바로 역할.
- 이때의 역할이 두 종류의 구체적인 객체를 포괄하는 추상화
- 역할은 다른 것으로 교체할 수 있는 책임의 집합이다.[Wirfs=Brock03]

### 역할의 구현

- 추상 클래스와 인터페이스를 사용
- 구체 클래스들이 따라야 하는 책임의 집합을 서술한 것
- 추상: 책임의 일부를 구현해 놓은 것 / 인터페이스: 일체의 구현 없이 책임의 집합만을 나열해 놓았다
- 다양한 종류의 클래스들을 협력에 참여시킬 수 있는 확장 포인트를 제공

### 객체 대 역할

- 여러 종류의 객체에 의해 수행될 필요가 있다 → 역할
- 한 종료의 객체만 협력에 참여할 필요가 있다 → 객체
- 협력 → 역할 → 객체 → 클래스
- 설계 초반에는 적절한 책임과 협력의 큰 그림을 탐색하는 것이 중요. 역할과 객체를 명확하게 구분하는 것은 그렇게 중요하지는 않다.
- 필요한 순간에 객체로부터 역할을 분리해내는 것이 좋다.
- 두 협력이 거의 유사한 구조를 보인다 → 하나로 합치면서 두 객체를 포괄할 수 있는 역할을 고려해서 객체를 역할로 대체
- 역할 모델링: 역할을 설계의 중심 개념으로 본다. UML에 큰 영향.
- 협력을 구체적인 객체가 아니라 추상적인 역할의 관점에서 설계. 설계의 구성 요소를 추상화할 수 있다.

### 역할과 추상화

- 역할은 객체의 추상화
- 불필요한 세부 사항을 생략하고 핵심적인 개념을 강조
- 협력의 관점에서는 세부 사항을 무시하고 추상화에 집중하는 것이 유용. 객체 사이의 핵심적인 상호작용이 더 또렷하게 드러난다.
- 기존 코드 수정 없이 새로운 행동 추가 가능
- 프레임워크나 디자인 패턴과 같이 재사용 가능한 코드나 설계 아이디어를 구성하는 핵심적인 요소가 바로 역할
- 연극 = 협력, 배역 = 역할, 배우 = 객체, 코드 = 극본,
- 역할은 객체가 협력에 참여하는 잠시 동안에만 존재하는 일시적인 개념. 객체의 페르소나.
- 객체는 여러 역할을 가질 수 있지만 특정한 협력 안에서는 일시적으로 오직 하나의 역할만이 보여진다.
- 동일한 역할을 수행하는 다양한 종류의 객체들은 다형적
