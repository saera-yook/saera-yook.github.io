이 장에서는 객체지향 설계에 대해 설명하고 책의 전체적인 주제를 함축해서 전달한다.
<br>책에서는 간단한 도메인을 구현한 코드와 함께 실용적인 예를 먼저 설명하지만 이 글에서는 설계와 객체지향에 대해 먼저 정리해보았다.

## 설계

로버트 마틴(Robert C. Martin)은 ⟪클린 소프트웨어: 애자일 원칙과 패턴, 그리고 실천 방법⟫[Martin2002a]에서 소프트웨어 모듈이 가져야 하는 세 가지 기능에 관해 아래와 같이 설명했다.

> 소프트웨어 모듈의 3가지 목적[Martin02]
> 1. 실행 중에 제대로 동작하는 것 - 모듈의 존재 이유.
> 2. 변경을 위해 존재하는 것 - 간단한 작업만으로도 변경이 가능해야 한다.
> 3. 코드를 읽는 사람과 의사소통하는 것 - 쉽게 읽고 이해할 수 있어야 한다.

프로그램이 오류 없이 제대로 동작하는 것은 프로그램이 갖춰야 할 가장 기본적인 조건이다.
<br>그렇다면 변경이 용이해야 하고, 이해하기 쉬워야 한다는 조건은 왜 중요할까?

변경을 수용할 수 있는 설계가 중요한 이유는 요구사항이 항상 변경되기 때문이다[Shalloway01].
<br>개발을 시작하는 시점에 구현에 필요한 모든 요구사항을 수집하는 것은 불가능에 가깝고, 개발이 진행되는 동안 요구사항은 바뀔 수밖에 없다.

또 다른 이유는 코드를 변경할 때 버그가 추가될 가능성이 높기 때문이다.
<br>코드를 수정하지 않는다면 버그는 발생하지 않는다. 다만 앞서 말한 이유 등에 의해 코드 수정은 불가피한데, 변경은 버그를 부르고 버그에 대한 두려움은 코드를 변경하기 어렵게 만든다.
<br>따라서 죽어있는 프로그램을 만들지 않으려면 변경하기 쉬운 설계가 중요하다.

또한, 변경과 의사소통이라는 문제는 서로 엮여 있다.
<br>하나의 클래스나 메서드에서 너무 많은 세부사항을 다루면 변경이 어려울뿐만 아니라, 코드를 작성하는 사람과 읽는 사람 모두에게 큰 부담을 준다.
<br>복잡한 클래스나 메서드의 의도를 정확하게 의사소통하지 못하게 되면 코드가 이해하기 어려워진다.
<br>이해 가능한 코드는 동작이 예상에서 크게 벗어나지 않는 코드이다.
<br>동작이 예상과 일치하는 이해하기 쉬운 코드는 변경이 용이할 가능성이 높다.

## 객체지향 설계

### 설계의 목표

마틴에 따른 소프트웨어 모듈의 3가지 목적을 만족하는 좋은 설계란 무엇일까?

> 오늘 완성해야 하는 기능을 구현하는 코드를 짜야 하는 동시에 내일 쉽게 변경할 수 있는 코드를 짜야 한다[Metz12].

- 필요한 최소한의 의존성만 유지하고 불필요한 의존성을 제거하는 것
- 객체 사이의 결합도를 낮춰 변경이 용이한 설계를 만드는 것

즉, 우리가 진정으로 원하는 것은 변경에 유연하게 대응할 수 있는 코드다.
<br>객체지향 프로그래밍은 의존성을 효율적으로 통제할 수 있는 다양한 방법을 제공함으로써 요구사항 변경에 좀 더 수월하게 대응할 수 있는 가능성을 높여준다.
<br>그렇다면 훌륭한 객체지향 설계란 무엇인지에 대해 이 책에서 언급된 내용들을 정리한 후에 그에 따른 설계 방법을 생각해보자.


### 훌륭한 객체지향 설계란

> > 불필요한 세부사항을 캡슐화하는 자율적인 객체들이
> > <br>낮은 결합도와 높은 응집도를 가지고 협력하도록
> > <br>최소한의 의존성만을 남기는 것
>
> 1. 소프트웨어를 구성하는 모든 객체들이 자율적으로 행동하는 설계
     >     - 적절한 객체에 적절한 책임을 할당하는 것
> 2. 서로 의존하면서 협력하는 객체들의 공동체를 구축하는 것
     >     - 객체 사이의 의존성을 완전히 없애는 것이 정답은 아니다.
> 3. 협력하는 객체 사이의 의존성을 적절하게 관리하는 설계
     >     - 캡슐화를 이용해 의존성을 적절히 관리함으로써 객체 사이의 결합도를 낮추는 것
     >     - 의존성을 적절하게 조절함으로써 변경에 용이한 설계를 만드는 것
>
> -⟪오브젝트⟫[조영호2006]


- 객체지향 안에는 단순히 데이터와 프로세스를 하나의 객체 안으로 모으는 것 이상의 무엇이 있다.
- 단순히 데이터와 프로세스를 객체라는 하나의 덩어리 안으로 밀어 넣었다고 해서 변경하기 쉬운 설계를 얻을 수 있는 것은 아니다.

### 설계 방법

- 외부의 간섭을 최대한 배제하고 메시지를 통해서만 협력하는 자율적인 객체들의 공동체를 만드는 것
- 객체가 어떤 데이터를 가지느냐보다는 객체에 어떤 책임을 할당할 것이냐에 초점

### 객체 사이의 의존성과 결합도

- 의존성은 변경에 대한 영향을 암시한다.
    - 어떤 객체가 변경될 때 그 객체에게 의존하는 다른 객체도 함께 변경될 수 있다는 사실이 내포돼 있다.
- 객체 사이의 의존성이 과한 경우 결합도가 높다고 말한다.
- 결합도가 높으면 높을수록 함께 변경될 확률도 높아지기 때문에 전체적으로 코드를 변경하기 어려워진다.
    - 어떤 클래스가 다른 클래스에 직접 접근한다는 것은 결합된다는 것을 의미한다.
    - 즉, 어떤 클래스가 다른 클래스의 내부에 대해 더 많이 알면 알수록 코드를 변경하기 어려워진다.
- 객체 간의 의존성은 설계를 어렵게 만들고, 애플리케이션을 수정하기 어렵게 만드는 주범이다.

#### 해결방법
- 객체를 자율적인 존재로 만들면 된다.
- 외부에서 너무 세세한 부분까지 알지 못하도록 정보를 차단. 알아야 할 필요가 없는 정보를 알지 못하도록.
- 불필요한 의존성을 제거 -> 객체 사이의 결합도를 낮추는 것
- 내부로 감춰 캡슐화 -> 객체의 자율성을 높이고 응집도 높은 객체들의 공동체를 창조
- 객체의 자율성을 높이는 방향으로 설계 -> 이해하기 쉽고 유연한 설계를 얻을 수 있다.

### 객체의 자율성, 캡슐화와 응집도

#### 캡슐화
- 개념적이나 물리적으로 객체 내부의 세부적인 사항을 감추는 것을 캡슐화라고 한다.
- 객체 내부의 상태를 캡슐화하고 객체 간에 오직 메시지를 통해서만 상호작용하도록 만드는 것
    - 객체를 인터페이스와 구현으로 나누고 인터페이스만을 공개하는 것
    - 내부에 인스턴스를 포함하고 있다는 사실은 구현의 영역
    - 외부 객체는 구현이 아닌 인터페이스에만 의존하도록
- 내부 구현이 캡슐화됐으므로 내부 구현을 수정하더라도 외부 객체에는 영항을 미치치 않는다.
- 내부 구현을 외부에 노출하지 않고 자신의 문제를 스스로 책임지고 해결하는 자율적인 존재가 된 것
#### 응집도
- 밀접하게 연관된 작업만을 수행하고 연관성 없는 작업은 다른 객체에게 위임하는 객체를 가리켜 응집도가 놓다고 말한다.
- 응집도를 높이기 위해서는 객체 스스로 자신의 데이터를 책임지고 처리하는 자율적인 존재여야 한다.
#### 자율성
- 즉, 캡슐화를 통해 자율적인 객체를 만들면 응집도를 높일 수 있고, 결합도를 낮출 수 있다.
- 결과적으로 변경이 용이하고 이해 가능한 코드를 작성할 수 있다.
- 자신의 데이터를 스스로 관리하고 문제를 스스로 해결하는 객체들로 구성된 코드는 변경이 용이하고 이해가 쉽다.
- 코드를 읽는 사람의 예상과도 일치하여 의사소통 관점에서도 개선된다.

## 설계와 트레이드오프

> 설계란 코드를 배치하는 것이다[Metz12].

- 설계를 구현과 떨어트려서 이야기하는 것은 불가능하다.
- 설계는 코드를 작성하는 매 순간 코드를 어떻게 배치할 것인지를 결정하는 과정에서 나온다.
- 설계는 코드 작성의 일부이며 코드를 작성하지 않고서는 검증할 수 없다.
- 하나의 기능을 구현하는 여러 방법의 코드를 배치하는 방법은 완전히 다르다. 서로 다른 설계를 가진 것.

### 트레이드오프
- 어떤 기능을 설계하는 방법은 한 가지 이상일 수 있다.
- 결국 설계는 트레이드오프의 산물이다.
- 어떤 경우에도 모든 사람들을 만족시킬 수 있는 설계를 만들 수는 없다.
- 설계는 균형의 예술이다. 훌륭한 설계는 적절한 트레이드오프의 결과물.
