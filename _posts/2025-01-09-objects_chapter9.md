## 개방-폐쇄 원칙[Martin02]

- 소프트웨어 개체(클래스, 모듈, 함수)는 확장에 대해 열려 있어야 하고, 수정에 대해 닫혀 있어야 한다.
  - 확장에 대해 열려있다: 요구사항 변경 시 새로운 '동작'을 추가해서 애플리케이션의 기능을 확장할 수 있다.
  - 수정에 대해 닫혀있다: 기존의 '코드'를 수정하지 않고도 동작을 추가하거나 변경할 수 있다.

### 컴파일타임 의존성을 고정시키고 런타임 의존성을 변경하라
### 추상화가 핵심이다
- 추상화에 의존하는 것
  - 추상화 부분은 수정에 대해 닫혀있다.
  - 추상화를 통해 생략된 부분은 확장의 여지를 남긴다.
- 모든 요소가 추상화에 의존해야 수정에 대해 닫혀있다.

## 생성 사용 분리
- 소프트웨어 시스템은 (응용 프로그램 객체를 제작하고 의존성을 서로 "연결"하는) 시작 단계와 (시작 단계 이후에 이어지는) 실행 단계를 분리해야 한다.[Martin08]
- 현재의 컨텍스트에 관한 결정권을 가지고 있는 클라이언트로 컨텍스트에 대한 지식을 옮김으로써 특정한 클라이언트에 결합되지 않고 독립적일 수 있다.

### FACTORY 추가하기
- 클라이언트도 특정 컨텍스트에 묶이지 않기를 바라면서 객체 생성과 관련된 지식이 클라이언트와 협력하는 클라이언트에게까지 새어나가지 않기를 원할 때
- 객체 생성과 관련된 책임만 전담하는 별도의 객체(FACTORY[Evans03])를 추가 -> 클라이언트가 이 객체를 사용 

### 순수한 가공물에게 책임 할당하기
- 순수한 가공물(PURE FABRICATION)[Larman04] 패턴
  - 책임을 할당하기 위해 창조되는 도메인과 무관한 인공적인 객체
  - 보통 특정한 행동을 표현
  - 행위적 분해에 의해 생성되는 것이 일반적
  - 데이터베이스 접근을 위한 객체와 같이 도메인 개념들을 초얼하는 기계적인 개념들을 필요로 할 수도
  - 설계자가 편의를 위해 임의로 만들어낸 가공의 객체
  - 정보 전문가 패턴에 따라 책임 할당한 결과 응집도가 낮아지고 결합도가 높아질 경우 대안으로 사용
- 표현적 분해
  - 시스템을 객체로 분해하는 방법 
  - 도메인에 존재하는 사물 또는 개념을 표현하는 객체들을 이용해 시스템을 분해
  - 도메인 모델의 개념과 관계를 따르며, 도메인과 소프트웨어 사이의 표현적 차이 최소화가 목적
- 애플리케이션 모델은 도메인 모델을 보충한다.(사용자에게 반응, 실행 제어, 외부 리소스에 연결하는 컴퓨터 객체를 이용해)[Wirfs-Brock03]

## 의존성 주입[Fowler04]
- 사용하는 객체가 아닌 외부의 독립적인 객체가 인스턴스 생성 후 전달해서 의존성 해결하는 방법
  - 생성자 주입
  - setter 주입
  - 메서드 (호출) 주입
  - 인터페이스 주입: setter 주입의 변형
    - 의존성을 명시하기 위해 인터페이스를 사용
    ```java
    public interface DiscountPolicyInjectable {
        void inject(DiscountPolicy discountPolicy);
    }

    // 주입받는 클래스가 인터페이스 구현
    ```

### 숨겨진 의존성은 나쁘다
- SERVICE LOCATOR 패턴[Alur03]
  - 의존성을 해결할 객체들을 보관하는 일종의 저장소
  - 객체가 직접 SERVICE LOCATOR에게 의존성을 해결해줄 것을 요청
  - 의존성을 숨긴다. 관련된 문제 발견 시점이 실행 시점(런타임)으로 미뤄진다.
  - 의존성을 이해하기 위해 코드 내부 구현을 이해해야. 캡슐화 위반
  - 단위 테스트 작성도 어렵다. 모든 단위 테스트 케이스에 걸쳐 상태를 공유. 단위 테스트의 기본 원칙 위반.
  - 호출 계층에 걸쳐 동일한 객체를 계속 전달해야 하는 고통이 큰 경우 어쩔 수 없이 사용하는 것을 고려
- 숨겨진 의존성은 의존성의 대상을 설정하는 시점과 의존성이 해결되는 시점을 멀리 떨어트려 놓는다 -> 코드 이해와 디버깅 어려움

## 의존성 역전 원칙
- 상위 수준의 모듈은 하위 수준의 모듈에 의존해서는 안 된다. 둘 모두 추상화에 의존해야 한다.
- 추상화는 구체적인 사항에 의존해서는 안 된다. 구체적인 사항은 추상화에 의존해야 한다.
- 전통적인 절차형 프로그래밍의 의존성 구조의 반대 방향
### 추상화와 의존성 역전
- 객체 사이 협력의 본질을 담고 있는 것은 상위 수준의 정책
- 상위 클래스가 하위 클래스에 의존한다면 하위 수준의 변경에 의해 상위 클래스가 영향
- 상위 수준의 변경으로 하위 수준이 영향을 받아야 함.
- 모든 의존성의 방향이 추상 클래스나 인터페이스와 같은 추상화를 따라야 함. 구체 클래스는 의존성의 시작점. 목적지가 돼서는 안됨.
### 의존성 역전 원칙과 패키지
- 역전은 인터페이스의 소유권에도 적용
- 코드의 컴파일이 성공하기 위해 함께 존재해야 하는 코드를 정의하는 것이 컴파일타임 의존성
- SEPARATED INTERFACE 패턴[Fowler02]
  - 추상화를 클라이언트가 속한 패키지에 포함시켜야
  - 함께 재사용될 필요가 없는 클래스들은 별도의 독립적인 패키지에 모아야
  - 불필요한 클래스들을 같은 패키지에 두면 빌드 시간을 가파르게 상승시킴
- 상위 수준의 협력 흐름을 재사용하기 위해서는 추상화가 제공하는 인터페이스의 소유권 역시 역전시켜야
- 인터페이스의 소유권을 서버가 아닌 클라이언트에 위치시킨다. 객체지향 프레임워크의 모듈 구조 설계 핵심 원칙

## 유연성에 대한 조언
### 유연한 설계는 유연성이 필요할 때만 옳다
- 유연한 설계 = 복잡한 설계
- 어떤 변경에 대비하기 위해 복잡하게 설계? 정말 유연성이 필요한가?
- 아직 일어나지 않은 변경은 변경이 아니다. 막연한 불안감은 불필요하게 복잡한 설계로
- 유연할수록 클래스 구조와 객체 구조 사이의 거리가 멀어진다. 단순성과 명확성 잃음
- 불필요한 SINGLETON 패턴[GOF94]은 객체 생성에 관해 너무 이른 시기에 고민, 결정할 때 도입되는 경향이 있음.
- 객체 생성은 모든 책임이 자리를 잡은 후 가장 마지막 시점에 내리는 것이 적절
