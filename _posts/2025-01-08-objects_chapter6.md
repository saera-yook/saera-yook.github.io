- 객체지향 애플리케이션의 가장 중요한 재료는 객체들이 주고받는 메시지다. 클래스 아님.
- 애플리케이션은 클래스로 구성되지만 메시지를 통해 정의된다[Metz12].

## 협력과 메시지

### 클라이언트-서버 모델[Wirfs-Brock90]
- 전송자: 클라이언트, 수신자: 서버
- 협력은 클라이언트가 서버의 서비스를 요청하는 단방향 상호작용
- 객체는 수신하는 메시지의 집합과 외부에 전송하는 메시지의 집합으로 구성됨
- 메시지 전송 = 메시지 수신자 + 메시지(오퍼레이션명 + 인자)
- 메시지를 수신했을 때 실제로 실행되는 함수 또는 프로시저를 메서드라고 부른다.
- 코드 상 동일한 이름의 변수에게 동일한 메시지를 전송해도 객체의 타입에 따라 실행되는 메서드가 달라질 수 있다.
- 기술적인 관점에서 메시지 전송은 전통적인 방식의 함수 호출이나 프로시저 호출과 다르다.
  - 객체는 메시지와 메서드라는 두 가지 서로 다른 개념을 실행 시점에 연결해야 -> 컴파일 시점과 실행 시점의 의미가 달라질 수 있다.
  - 메시지 전송과 메서드 호출을 명확하게 구분. 실행 시점에 메시지를 메서드에 바인딩. -> 전송자와 수신자가 느슨하게 결합되도록

### 퍼블릭 인터페이스와 오퍼레이션
- 프로그래밍 언어 관점에서 퍼블릭 인터페이스에 포함된 메시지를 오퍼레이션이라고 부른다.
- 오퍼레이션: 수행 가능한 어떤 행동에 대한 추상화. 내부 구현 코드 제외하고 메시지와 관련된 시그니처를 가리키는 경우가 대부분. e.g.추상 클래스의 추상 메서드
- 메서드: 메시지 수신 시 실제로 실행되는 코드 e.g. 추상 클래스를 상속한 자식 클래스의 오버라이딩 메서드(오퍼레이션의 구현이 메서드)
- 클라이언트(전송자)가 메시지를 전송하면 런타임 시스템은 메시지 전송을 오퍼레이션 호출로 해석 -> 수신자의 실제 타입을 기반으로 적절한 메서드를 찾아 실행
- 퍼블릭 인터페이스와 메시지 관점에서 메서드 호출 보다는 오퍼레이션 호출이 더 적절

### 시그니처
- 오퍼레이션의 이름과 파라미터 목록을 합친 것
- 오퍼레이션은 실행 코드 없이 시그니처만을 정의한 것. 메서드는 이 시그니처에 구현을 더한 것.
- 오퍼레이션 관점에서 다형성이란 동일한 오퍼레이션 호출에 대해 서로 다른 메서드들이 실행되는 것(하나의 오퍼레이션에 대해 다양한 메서드를 구현)

## 인터페이스와 설계 품질
- 최소한의 인터페이스: 꼭 필요한 인터페이스만 포함, 추상적인 인터페이스: 어떻게가 아니라 무엇을 하는지 표현 = 좋은 인터페이스

### 디미터 법칙
- 객체의 내부 구조에 강하게 결합되지 않도록 협력 경로를 제한하라
- 낯선 자에게 말하지 말라[Larman04]
- 오직 인접한 이웃하고만 말하라. 오직 하나의 도트만 사용하라[Metz12]
- 클래스가 특정 조건을 만족하는 대상에게만 메시지를 전송하도록 프로그래밍
    - 모든 클래스와 그 안에 구현된 메서드에 대해서 메시지를 전송할 수 있는 모든 객체는 아래 클래스의 인스턴스여야
      - 메서드의 인자로 전달된 클래스(메서드가 구현된 클래스 자체 포함)
      - 메서드가 구현된 클래스의 인스턴스 변수의 클래스
    - 아래 조건을 만족하는 인스턴스에게만
      - this 객체
      - 메서드의 매개변수
      - this의 속성
      - this의 속성인 컬렉션의 요소
      - 메서드 내에서 생성된 지역 객체
- 부끄럼타는 코드(shy code)[Hunt99]: 불필요한 것 보여주지 않고, 다른 객체의 구현에 의존하지 않는 코드
- 협력하는 클래스의 캡슐화를 위해 접근해야 하는 요소를 제한
- 위반 예
  - screening.getMovie().getDiscountConditions();
  - 전송자가 수신자의 내부 구조를 물어봄 -> 반환받은 요소에 대해 연쇄적으로 메시지를 전송: 기차 충돌(train wreck)[Martin08]
  - 클래스 내부 구현이 외부로 노출됐을 때 나타나는 전형적인 형태
  - 내부 구조를 묻는 메시지가 아니라 수신자에게 무언가를 시키는 메시지가 더 좋다.

### 묻지 말고 시켜라
- 절차적인 코드는 정보를 얻은 후에 결정한다. 객체지향 코드는 객체에게 그것을 하도록 시킨다.[Sharp00]
- 내부의 상태를 이용해 어떤 결정을 내리는 로직이 객체 외부에 존재한다면 해당 객체의 책임이 외부로 누수된 것
- 객체는 내부적으로 보유하고 있는 정보나 메시지 전송의 결과로 얻게 되는 정보만 사용해서 의사결정을 내린다.

### 의도를 드러내는 인터페이스
- 메서드 명명 방법
  - 작업을 어떻게 수행하는지 나타내도록
    - 내부 구현을 드러냄
    - 커뮤니케이션 못함. 비슷한 메서드 내부 구현 모르면 동일한 작업을 수행한다는 것을 알 수 없음
    - 메서드 수준에서 캡슐화 위반. 메서드 이름을 변경한다는 것은 메시지를 전송하는 클라이언트의 코드도 함께 변경해야 한다는 것을 의미. 변경에 취약.
  - 무엇을 하는지를 드러내는 것 - 의도를 드러내는 선택자
    - 협력하는 클라이언트의 의도에 부합하도록 메서드의 이름을 짓게 된다.
    - 자바에서는 단순히 메서드 이름이 같다고 동일한 메시지를 처리할 수 있는 건 아님. 동일한 타입 계층으로 묶어야. 인터페이스나 추상클래스 사용.
    - 구현 하나인 메시지 이름을 일반화 방법: 매우 다른 두 번째 구현을 상상하고 동일한 이름을 붙인다고 상상하기. 가능한 가장 추상적인 이름을 붙일 것.[Beck96]
- 결과와 목적만 포함하도록 클래스와 오퍼레이션의 이름을 부여하라. 클라이언트 개발자가 내부를 이해해야 할 필요성이 줄어든다. 도메인의 퍼블릭 인터페이스에서는 관계와 규칙을 시행하는 방법이 아닌 이벤트와 규칙 그 자체만 명시한다.[Evans03]

### 함께 모으기
- 디미터 법칙 위반 -> 인터페이스와 구현의 분리 원칙 위반
- 퍼블릭 인터페이스 이름으로 코드의 목적을 명확하게 커뮤니케이션 할 수 있어야.


## 원칙의 함정
- 원칙이 서로 충돌하는 경우에도 원칙에 정당성을 부여하고 억지로 끼워 맞추려고 노력하지 말라
- 현재 상황에 부적합하다고 판단 -> 과감히 버려라. 원칙을 아는 것보다 언제 유용하고 언제 그렇지 않은지 아는 것이 중요

### 디미터 법칙은 하나의 도트(.)를 강제하는 규칙이 아니다
- e.g. Stream: 동일한 클래스 인스턴스를 반환할 뿐 객체를 둘러싸고 있는 캡슐은 그대로 유지된다. 객체 내부에 대한 어떤 내용도 묻지 않는다. 단지 객체 변환 작업을 시킬뿐 
- 디미터 법칙은 결합도와 관련. 결합도 문제는 객체의 내부 구조가 외부로 노출되는 경우로 한정.

### 결합도와 응집도의 충돌
- 어떤 객체의 상태를 물어본 후 반환된 상태를 기반으로 결정을 내리고 그 결정에 따라 객체의 상태를 변경하는 코드는 묻지 말고 시켜라 스타일로 변경해야
- 가끔씩은 묻는 것 외에는 다른 방법이 존재하지 않는 경우도 있다. 컬렉션에 포함된 객체들을 처리하는 유일한 방법은 객체에게 물어보는 것이다.
- 디미터 법칙의 위반 여부는 묻는 대상이 객체인지, 자료 구조인지에 달려있다.[로버트 마틴<<클린 코드>>08]
- 자료 구조라면 당연히 내부를 노출해야 하므로 디미터 법칙을 적용할 필요가 없다.

## 명령-쿼리 분리 원칙
- 루틴: 어떤 절차를 묶어 호출 가능하도록 이름을 부여한 기능 모듈
  - 프로시저: 정해진 절차에 따라 내부의 상태를 변경. 부수효과 발생 가능. 값 반환 불가능. = 명령: 객체의 상태를 수정하는 오퍼레이션
  - 함수: 절차에 따라 필요한 값을 계산해서 반환. 부수효과 불가능. 값 반환 가능. = 쿼리: 객체와 관련된 정보를 반환하는 오퍼레이션
- 어느 오퍼레이션도 명령인 동시에 쿼리여서는 안 된다. 질문이 답변을 수정해서는 안 된다.
- 기계 메타포: 객체 = 블랙박스, 인터페이스 = 관찰 가능한 상태를 보기 위한 일련의 디스플레이 + 상태를 변경하기 위해 누를 수 있는 버튼

### 반복 일정의 명령과 쿼리 분리하기
- 명령과 쿼리를 뒤섞으면 실행 결과를 예측하기 어려워진다.
- 겉으로 보기에는 쿼리처럼 보이지만 내부적으로 부수효과를 가지는 메서드는 이해 어렵고, 잘못 사용하기 쉬움, 버그를 양산하는 경향
- 쿼리는 부수효과에 대한 부담이 없다. 몇 번을 호출해도 다른 부분에 영향을 미치지 않는다. 명령 호출 없이 쿼리만 연속 호출하면 같은 결과가. 순서도 상관 없음 자유롭게 변경 가능.
- 명령 호출 시 부수효과에 주의.

### 명령-쿼리 분리와 참조 투명성
- 프로그램에서 부수효과 발생시키는 대표적 문법: 대입문, 프로시저
- 참조 투명성[Meyer00]: 어떤 표현식 e가 있을 때 e의 값으로 e가 나타나는 모든 위치를 교체하더라도 결과가 달라지지 않는 특성
  - 모든 함수를 이미 알고 있는 하나의 결과값으로 대체 가능. 식을 쉽게 계산 가능
  - 모든 곳에서 함수의 결과값이 동일. 식의 순서를 변경해도 각 식의 결과는 달라지지 않는다.
  - 명령과 쿼리를 분리해 제한적으로나마 쿼리에 대해 가능
- 명령형 프로그래밍과 함수형 프로그래밍
  - 명령형: 부수효과 기반. 상태를 변경시키는 연산들을 적절한 순서로 나열해 프로그램 작성. 대부분의 객체지향 프로그래밍 언어들. 메시지에 의한 객체의 상태 변경에 집중
  - 함수형: 부수효과가 존재하지 않는 수학적인 함수에 기반. 참조 투명성의 장점 극대화. 실행 결과 이해 및 예측이 더 쉽다.
  - 하드웨어 발달로 병렬 처리가 중요해진 최근에는 함수형 인기가 상승. 객체지향 언어들도 함수형 패러다임을 접목시키고 있는 추세

### 책임에 초점을 맞춰라
- 협력을 위해 두 객체가 보장해야 하는 실행 시점의 제약을 인터페이스에 명시할 수 있는 방법이 없음.
- 계약에 의한 설계[버트란드 마이어(부록A 참고)]
  - 협력을 위해 클라이언트와 서버가 준수해야 하는 제약을 코드 상에 명시적으로 표현하고 강제할 수 있는 방법
